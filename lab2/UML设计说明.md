## 1. 设计范围

系统以账本为权限和数据边界，按“身份与认证、账本与成员、账目与审批、结算、查询与导出、审计与通知”六个业务模块组织。手机应用与微信小程序共享同一后端和同一套业务规则；系统只记录账目并生成结算报告，不执行真实资金转账。

| 模块 | 主要职责 | 核心需求 |
| --- | --- | --- |
| 身份与认证 | 用户身份、用户名密码认证、多认证方式绑定同一账号的扩展点 | `REQ-027` |
| 账本与成员 | 创建账本、邀请成员、角色与账本级权限隔离、再次加入隔离 | `REQ-001`、`REQ-006`、`REQ-019`、`REQ-031` |
| 账目与审批 | 新增/修改申请、审批、直接维护、免审、撤销、修改记录、账目状态 | `REQ-002` 至 `REQ-006`、`REQ-013` 至 `REQ-017`、`REQ-025`、`REQ-030` |
| 结算 | 平均/手工分摊、净额计算、尾差累积、报告生成、标记已结清 | `REQ-008` 至 `REQ-010`、`REQ-018`、`REQ-021`、`REQ-024` |
| 查询与导出 | 按时间、类别和垫付成员筛选，导出当前筛选结果 | `REQ-011`、`REQ-012`、`REQ-026` |
| 审计与通知 | 全操作日志、管理员及以上查看日志、应用内通知创建者 | `REQ-007`、`REQ-020`、`REQ-029` |

## 3. 关键设计说明

### 3.1 类图

- `LedgerMembership` 将“用户”和“账本”的多对多关系显式建模，角色只在该账本内有效；同一用户退出后重新加入会产生新的成员关系，结算按成员关系 ID 分组而不是按用户 ID 合并。
- `ExpenseEntry` 保存创建者、垫付者、发生时间和可选的原账目引用；金额使用 `DECIMAL(20,6)` 与 `BigDecimal`，禁止使用浮点数。
- `ApprovalRequest` 与 `ChangeRecord` 分离：前者保存待审业务申请，后者保存已经生效的修改历史，避免审批数据覆盖账目历史。
- `SplitStrategy` 使用策略模式，将平均分摊与手工分摊从账目实体中解耦，后续增加分摊方式不需要修改账目核心类。
- `SettlementLine` 保存每个历史成员关系的精确净额、零和量化净额和期末尾差；`SettlementTransfer` 保存债务成员到债权成员的具体付款指令。
- `RoundingBalance` 按“账本 + 历史成员关系”保存期末尾差，只保留非零行；整本账的所有成员尾差之和必须为零。
- 删除、作废与撤销统一映射为 `REVOKED`，不存在独立的“已作废”状态。

### 3.2 组件图

- 客户端层只负责界面和请求封装，手机应用与微信小程序通过同一 API 网关访问后端。
- 业务模块按高内聚职责拆分。账目与审批模块依赖账本与成员模块读取角色和免审配置，结算模块读取未结算账目、成员关系与尾差。
- `PermissionPolicy` 是横切业务组件，所有账本相关操作都必须先校验目标账本内的角色，不能只依据用户全局身份。
- `Audit & Notification` 集中处理留痕与通知，避免各模块重复实现日志逻辑。
- 统一数据访问组件隔离业务模块与数据库，结算中的报告、结清状态、尾差和审计日志需要同一事务提交。

### 3.3 用例图与角色边界

- 所有者继承管理员的全部显式权限，并额外拥有设置成员角色、配置免审的能力。
- 普通成员可提交新增/修改申请、查询账目和查看通知，但不能审批、直接维护、撤销或结算。
- 只读访客只能查看与筛选，不授予导出权限；普通成员及以上角色可导出。
- 审批、直接维护、撤销和结算均须审计留痕；审批结果还需要通知账目创建者。

### 3.4 活动图

活动图覆盖普通成员提交申请后的两条路径：命中免审时直接写入并留痕；未命中免审时进入待审核，由管理员批准或驳回。校验失败会在写入前终止，避免产生无效账目。

### 3.5 状态图

状态图按设计决策绘制完整流转：待审核账目可由申请人撤回至草稿；驳回记录保持只读，可复制为新草稿；已结清和已撤销账目不做原地恢复，订正通过关联原账目的新账目完成。

### 3.6 时序图

时序图展示管理员发起结算时的调用顺序：权限校验、读取全部未结算账目和期初尾差、逐条计算精确分摊、由 `SettlementMatcher` 完成零和量化与债务匹配、保存付款指令和成员尾差、标记已结清、记录审计日志并原子提交。首版不支持部分结算，并使用幂等键防止重复提交；系统不存在真实转账调用。

## 4. 模块交互摘要

| 发起模块 | 目标模块 | 交互内容 |
| --- | --- | --- |
| 客户端 | API 网关 | 提交请求、接收响应，不直接访问数据库 |
| API 网关 | 身份与认证 | 认证用户并建立当前身份上下文 |
| 账本与成员 | 权限策略 | 提供账本角色，支持账本级权限判断 |
| 账目与审批 | 账本与成员 | 读取成员资格、垫付者约束和免审配置 |
| 账目与审批 | 审计与通知 | 记录申请/审批/修改/撤销日志，通知账目创建者 |
| 结算 | 账目与审批 | 读取未结算账目并将其标记为已结清 |
| 结算 | 账本与成员 | 读取成员关系与账本尾差余额 |
| 查询与导出 | 账本与成员、账目与审批 | 校验可见范围，筛选并导出账目 |
| 所有业务模块 | 数据访问层 | 持久化领域对象，结算操作使用事务保证一致性 |

## 5. 与实验一基本模块的对应

实验一明确的基本业务模块均已进入组件图和用例图，并在类图中有承载对象：

- 账本创建与成员角色：`Ledger`、`LedgerMembership`、`LedgerRole`。
- 普通成员申请新增/修改与管理员审批：`ExpenseEntry`、`ApprovalRequest`。
- 管理员直接维护、撤销与所有者免审：`ExemptionRule`、`ChangeRecord`、`EntryStatus`。
- 按分摊方式结算并生成报告：`SplitStrategy`、`SplitShare`、`SettlementReport`、`SettlementLine`、`SettlementTransfer`、`RoundingBalance`。
- 查询与导出：组件图中的 `Query & Export` 模块。
- 审计与通知：`AuditLog`、`Notification` 及 `Audit & Notification` 组件。
- 用户身份：`UserAccount`、`AuthBinding` 与 `Identity & Auth` 组件。

## 6. 渲染说明

在 `lab2/` 目录中执行以下命令，可为每个 `.puml` 文件生成同名 PNG：

```powershell
java -jar plantuml.jar -charset UTF-8 "UML/*.puml"
```

如果 PlantUML 位于其他路径，请替换 `plantuml.jar` 为实际路径。图片渲染后需检查中文、连线、多重度和图例是否清晰。
