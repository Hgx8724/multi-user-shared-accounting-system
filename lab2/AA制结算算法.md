# AA 制结算算法设计

- 项目名称：在线多人记账系统
- 适用范围：账目分摊、成员净额计算、债务人与债权人匹配、尾差处理
- 相关需求：`REQ-008`、`REQ-009`、`REQ-010`、`REQ-018`、`REQ-021`、`REQ-031`

## 1. 设计结论

AA 制结算不能依赖一个无主的“尾差池”。例如：

```text
A: +13.34
B: -6.66
C: -6.66
```

三项相加为 `+0.02`，并不是完整结算结果，因此无法客观判断这 `0.02` 属于谁。

本设计采用以下原则：

1. 金额使用 `DECIMAL(20,6)` 和 `BigDecimal`，禁止浮点数。
2. 所有结算均以成员关系 `membershipId` 为单位，不以用户账号为单位合并。
3. 先计算精确净额，再将其量化为整数分，量化后的所有成员净额必须严格相加为零。
4. 债务人可以同时向多个债权人付款，债权人也可能收到多个债务人的付款。
5. 分摊尾差必须在量化时分配给具体成员关系，并保存来源，不保留无主金额。
6. 结算报告同时保存精确净额、整数分净额、付款指令和期末尾差。

## 2. 核心数据

| 数据 | 含义 |
| --- | --- |
| `ExpenseEntry.amount` | 账目总金额，`DECIMAL(20,6)` 元 |
| `SplitShare.membershipId` | 该分摊所属的历史成员关系 |
| `SplitShare.amount` | 该成员关系的精确分摊金额 |
| `SettlementLine.exactNetAmount` | 加入期初尾差后的精确净额 |
| `SettlementLine.finalNetAmount` | 零和量化后的整数分净额 |
| `SettlementLine.closingRoundingAmount` | 本次结算结束时保留给该成员关系的尾差 |
| `SettlementTransfer` | 从债务成员关系指向债权成员关系的付款指令 |
| `RoundingBalance` | 按账本和成员关系保存的期末尾差，正数表示待收，负数表示待付 |

`RoundingBalance` 必须满足：

```text
sum(all RoundingBalance.amount for a ledger) = 0
```

即整本账的尾差余额合计必须为零，不能只有某个成员单边存在尾差。

## 3. 算法流程

### 3.1 第一步：锁定账本

结算请求必须携带 `Idempotency-Key`，并锁定目标账本、相关账目和尾差余额行。

同一幂等键重复提交时，直接返回原结算报告，不重复生成付款指令。

### 3.2 第二步：计算精确净额

先取得所有未结算且已生效的账目，再按成员关系汇总：

```text
exactNet(membership)
  = 该成员关系的垫付总额
  + 该成员关系的期初尾差
  - 该成员关系的精确分摊总额
```

其中分摊金额使用精确小数计算。平均分摊时，内部金额至少保留 6 位小数；如果除法无法整除，也需要把最小精度余量分配给具体成员，使每条账目的分摊合计严格等于账目金额。

所有成员的精确净额之和必须为零：

```text
sum(exactNet) = 0
```

### 3.3 第三步：零和量化到分

设成员 `i` 的精确净额换算成分后的值为 `e_i`。

1. 计算 `floor_i = floor(e_i)`。
2. 计算小数部分 `fraction_i = e_i - floor_i`。
3. 计算需要补充的整数分数量 `K = -sum(floor_i)`。
4. 按 `fraction_i` 从大到小排序，向前 `K` 个成员各增加 1 分。
5. 得到量化净额 `c_i`。

必须满足：

```text
sum(c_i) = 0
```

当多个成员的小数部分完全相同时，使用账本级轮转游标决定谁获得额外 1 分，再以成员关系 ID 作为最终稳定的决胜条件。轮转游标会持久化，避免长期总是同一个成员承担取整差异。

量化后的净额用于生成付款指令；精确净额与量化净额之间的差值就是该成员的本期期末尾差。

### 3.4 第四步：匹配债务人与债权人

根据量化净额划分：

- `c_i > 0`：债权人，应收 `c_i`。
- `c_i < 0`：债务人，应付 `abs(c_i)`。
- `c_i = 0`：无需付款或收款。

采用确定性的双指针匹配：

1. 债务人按应付金额从大到小排序。
2. 债权人按应收金额从大到小排序。
3. 取当前最大债务人和最大债权人。
4. 生成金额为两者较小值的付款指令。
5. 扣减双方余额，余额为零的一方从队列移除。
6. 重复直到所有余额结清。

该方法保证：

- 每条付款边金额为正整数分。
- 债务人不会向自己付款。
- 所有付款边金额之和等于全部债权人应收金额。
- 一个债务人可以生成多条付款边，一个债权人也可以收到多条付款边。
- 在量化净额严格零和的前提下，所有余额都会完全结清。

双指针匹配是线性、可复现的常用方案，优先减少参与者数量和付款边数量，但不承诺在所有复杂数据上取得理论意义上的全局最少边数。

匹配伪代码：

```text
creditors = sortDesc(netAmount > 0)
debtors   = sortDesc(abs(netAmount) for netAmount < 0)

while debtors is not empty and creditors is not empty:
    debtor = debtors.first
    creditor = creditors.first
    amount = min(debtor.remaining, creditor.remaining)
    append Transfer(debtor.membershipId, creditor.membershipId, amount)
    debtor.remaining -= amount
    creditor.remaining -= amount
    remove queue head when remaining == 0

assert sum(transfers.from) == sum(transfers.to)
assert all member remaining == 0
```

### 3.5 第五步：保存结果

必须在同一个数据库事务中完成：

1. 保存结算报告和成员结算明细。
2. 保存所有付款指令 `SettlementTransfer`。
3. 更新每个成员关系的期末尾差 `RoundingBalance`。
4. 将纳入结算的账目标记为已结清。
5. 写入审计日志。

任何一步失败都必须整体回滚。

## 4. 尾差归属规则

尾差不存在“账本公共余额”这一归属。它必须落到具体成员关系：

```text
closingRoundingAmount_i = exactNet_i - finalNet_i
```

并且：

```text
sum(closingRoundingAmount_i) = 0
```

因此：

- 如果某人多收或少收了几分钱，其尾差余额记录在该成员关系下。
- 不能只记录一个账本级 `0.02` 然后事后推断属于谁。
- 下一周期先把这些成员级尾差加入精确净额，再重新量化并匹配。
- 尾差随原始成员关系保存；成员退出不会删除，重新加入也不会自动继承。

## 5. 示例一：A 支付 20 元，三人平分

精确净额：

```text
A = +13.333333
B = -6.666667
C = -6.666667
```

假设本轮轮转游标把额外 1 分分配给 A，则零和量化结果为：

```text
A = +13.34
B = -6.67
C = -6.67
```

付款指令：

```text
B -> A  6.67
C -> A  6.67
```

期末尾差：

```text
A = -0.006667
B = +0.003333
C = +0.003333
```

此时报告合计为零。不能使用 `A +13.34, B -6.66, C -6.66` 作为最终结果，因为它合计为 `+0.02`。

## 6. 示例二：A 支付 13 元、B 支付 7 元，三人平分

精确净额：

```text
A = +6.333333
B = +0.333333
C = -6.666667
```

假设本轮轮转游标把额外 1 分分配给 A，则零和量化结果为：

```text
A = +6.34
B = +0.33
C = -6.67
```

付款指令：

```text
C -> A  6.34
C -> B  0.33
```

期末尾差：

```text
A = -0.006667
B = +0.003333
C = +0.003333
```

这里 C 必须同时向 A 和 B 付款。只让 C 付给 A 6.34 元、让 B 收不到钱，不是完整结算。

## 7. 轮转公平性

由于小数部分相同的成员可能有多个，必须定义稳定的决胜顺序：

1. 比较精确净额的小数部分，数值大者优先获得额外 1 分。
2. 小数部分相同时，从账本级轮转游标指示的成员开始，按成员关系 ID 循环选择。
3. 结算成功后推进游标。
4. 游标推进和结算结果在同一事务中提交。

这样可以避免固定偏向成员关系 ID 最小或创建时间最早的成员。

## 8. 成员退出与重新加入

- 结算明细、付款指令和尾差均绑定 `membershipId`。
- 成员退出后，历史成员关系仍可产生应收、应付和尾差。
- 重新加入会生成新的成员关系，新关系不能继承旧关系的尾差。
- 同一用户拥有旧、新两段成员关系时，报告中分别显示两条记录。
- 若两个债权成员关系属于同一用户，付款方仍可在界面看到合并后的收款人，但数据库必须保留两条归属记录。

## 9. 边界规则

| 场景 | 处理 |
| --- | --- |
| 没有未结算账目 | 不生成报告，提示无可结算内容 |
| 只有一个成员 | 精确净额应为零，不生成付款指令 |
| 手工分摊合计不等于账目金额 | 拒绝提交 |
| 某个成员净额为零 | 不进入债务人或债权人队列 |
| 债务人和债权人金额完全相等 | 生成一笔付款边后全部结清 |
| 成员被移除 | 保留历史成员关系和债务，不重新分摊 |
| 成员重新加入 | 创建新成员关系，旧尾差不继承 |
| 同一请求重复提交 | 返回原报告，不重复生成转账边 |
| 结算期间账目被修改 | 版本冲突，整笔回滚 |

## 10. 算法不变量与测试

每次结算必须验证：

1. 每条账目的分摊总额等于账目金额。
2. 所有精确净额之和为零。
3. 所有量化整数分净额之和为零。
4. 所有期末尾差之和为零。
5. 每条付款指令金额大于零。
6. 不产生自己向自己付款。
7. 所有付款指令的总额等于所有债务人的应付总额。
8. 重复执行同一幂等请求不会产生新付款指令。
9. 成员退出、重新加入不会改变历史成员关系上的金额归属。
10. 小数部分相同的成员在连续结算中能获得轮转公平。

## 11. 与 UML 的对应

- `SplitShare` 保存精确分摊所属的成员关系。
- `SettlementLine` 保存精确净额、量化净额和期末尾差。
- `SettlementTransfer` 保存债务人与债权人之间的付款边。
- `RoundingBalance` 按成员关系保存尾差，不按用户合并。
- 时序图中的 `SettlementMatcher` 执行零和量化与债务匹配。
- 报告生成、付款指令、尾差更新和账目结清必须共用同一事务。

本算法取代此前“由垫付人单独吸收尾差”的简化方案。所有未达一分的差异都必须落到具体成员关系，并在报告中可追溯。
