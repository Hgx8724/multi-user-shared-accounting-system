# 通用结账算法设计

- 项目名称：在线多人记账系统
- 适用范围：不同分摊成员、不同分摊策略、多付款人、跨账目结算
- 相关需求：`REQ-008`、`REQ-009`、`REQ-010`、`REQ-018`、`REQ-021`、`REQ-024`、`REQ-031`

## 1. 核心原则

1. 分摊方案属于账目，不属于结算周期。
2. 结算阶段不再选择成员，也不再选择分摊策略。
3. 所有账目金额、付款金额和分摊金额最终都归一为整数分。
4. 平均分摊除不尽时，余数分必须在账目分摊时分配给具体成员。
5. 成员净额全部为整数分，结算付款匹配不需要再做金额量化。
6. 每笔账目的分摊方案必须满足：

```text
sum(分摊金额) = 账目金额
sum(付款金额) = 账目金额
```

7. 结算只负责汇总所有账目并匹配债务人和债权人。

## 2. 金额表示

数据库可以使用精确的 `DECIMAL(20,2)` 保存元金额，应用层使用语言提供的精确十进制类型（C# 使用 `decimal`）；进入分摊和结算计算时统一转换为整数分：

```text
amountCents = amount.setScale(2, RoundingMode.UNNECESSARY)
                    .movePointRight(2)
                    .longValueExact()
```

禁止使用 `float`、`double` 或未定义精度的连续除法。

用户输入的最小单位为 `0.01` 元。平均分摊不保存 `6.666667` 这类循环小数，而是直接保存分配后的整数分：

```text
20.00 元 = 2000 分
2000 / 3 = 666 ... 2
基础分摊 = 666 分/人
余数 = 2 分
```

余数按确定性规则分配给具体成员，确保三人分摊合计严格等于 2000 分。

## 3. 数据结构

| 数据                 | 含义                             |
| -------------------- | -------------------------------- |
| `ExpenseEntry`       | 一笔账目的总额、时间和状态       |
| `ExpensePayment`     | 一名成员实际支付的金额，可有多条 |
| `ExpenseSplitPlan`   | 该账目冻结的成员集合和分摊方式   |
| `SplitShare`         | 每个成员的整数分分摊额           |
| `SettlementReport`   | 一次结算的汇总快照               |
| `SettlementLine`     | 每个历史成员关系的净额           |
| `SettlementTransfer` | 债务成员到债权成员的付款指令     |

`ExpenseSplitPlan` 属于单笔 `ExpenseEntry`。不同账目可以使用不同成员和不同策略。

## 4. 账目分摊阶段

账目提交或修改时执行以下流程：

1. 选择一名或多名实际付款成员并填写付款金额。
2. 选择至少一名分摊成员。
3. 选择平均分摊或手工分摊。
4. 将金额转换为整数分。
5. 生成并校验 `ExpenseSplitPlan` 和 `SplitShare`。
6. 冻结方案，后续结算不得改选成员或重算策略。

### 4.1 平均分摊

设账目总金额为 `totalCents`，已选分摊成员数为 `n`：

```text
base = totalCents / n
remainder = totalCents % n
每个成员先分配 base 分；
再将剩余 remainder 分按 1 分/人分配给具体成员。
```

为处理不同账目、不同参与成员集合，不能只依赖一个全局游标。系统为每个“账本 + 成员关系”保存一个精确的累计舍入应得额（`RoundingAllocationState`），以分数形式记录尚未获得的余数分权益。

每次平均分摊执行：

1. 对每个已选成员增加本次理论余数权益 `remainder / n` 分。
2. 从当前累计应得额最大的成员开始，选出 `remainder` 名成员各分配 1 分。
3. 每分配 1 分，从该成员累计应得额中扣除 1 分。
4. 应得额相同时，使用账本级轮转游标和成员关系 ID 决胜。
5. 保存本次分摊前后的游标和每个成员的舍入调整。
6. 所有成员的累计应得额始终精确合计为零。

该算法不是简单的固定轮询：参与次数多、应得余数分多但尚未获得补偿的成员会优先获得下一次余数分；没有被选入某笔账目分摊的成员不会凭空增加权益。

为了保证跨不同成员集合仍公平，舍入应得额必须按成员关系独立保存，不能只保存一个账本级游标。`RoundingAllocationState` 使用任意精度整数分子和分母保存精确分数（C# 使用 `System.Numerics.BigInteger`），不使用浮点数。

公平性约束：

- 任一成员的实际余数收益与理论应得额之差小于 1 分。
- 长期重复相同参与者场景下，额外 1 分获得频率趋近于 `remainder / n`。
- 不同参与者集合下，只有实际被选入该账目的成员增加本次应得额。
- 游标只用于相同应得额时的平分决胜，不单独决定分配结果。
- 分摊方案变为 `ACTIVE` 时才更新公平状态；草稿和待审核方案不能提前占用余数分。
- 已生效方案被修改时，先冲销旧方案记录的舍入调整，再应用新方案，整个过程在同一事务中完成。
- 成员退出后其历史公平状态保留；重新加入仍是同一个稳定 `LedgerMembership`，游标和舍入应得额不从零重置。
- 所有公平状态的分子/分母更新必须和 `SplitShare` 保存处于同一事务。

例如 20.00 元由 A、B、C 平均分摊：

```text
base = 666 分
remainder = 2 分
```

假设本轮余数分给 A、B：

```text
A = 667 分 = 6.67 元
B = 667 分 = 6.67 元
C = 666 分 = 6.66 元
```

三人的分摊金额合计严格等于 20.00 元，不存在循环小数或未归属尾差。

### 4.2 手工分摊

1. 用户为每个已选成员填写金额。
2. 输入金额必须精确到分。
3. 每个已选成员的金额必须大于 0。
4. 手工金额集合的键必须与已选成员集合完全一致。
5. 所有金额合计必须等于账目金额。

手工分摊不参与余数分配，校验通过后直接保存到 `SplitShare`。

例如账目 20.00 元，选择 A、B、C，手工填写：

```text
A = 5.00
B = 7.00
C = 8.00
```

保存结果为：

```text
SplitShare(A, 500)
SplitShare(B, 700)
SplitShare(C, 800)
```

如果合计不等于 2000 分，整笔提交失败，不自动平均，也不自动补到某个成员。

### 4.3 单人承担

只选择一名成员时，平均分摊和手工分摊都等价于该成员承担全部账目金额：

```text
A = 0 分
B = 0 分
C = 2000 分
```

该成员可以是实际付款人，也可以不是实际付款人。

## 5. 结算阶段

结算阶段不选择成员，也不执行分摊策略，只读取已冻结的账目快照。

### 5.1 汇总成员净额

对每个历史成员关系 `membershipId`：

```text
netCents(membership)
  = sum(实际付款金额)
  - sum(该成员关系的分摊金额)
```

由于每条账目都满足：

```text
sum(分摊金额) = 账目金额
sum(付款金额) = 账目金额
```

所以所有成员净额必须是整数分，并且：

```text
sum(netCents) = 0
```

不再存在需要跨周期结转的“账本公共尾差”。

### 5.2 匹配债务人与债权人

将净额分为：

- `netCents > 0`：债权人，应收。
- `netCents < 0`：债务人，应付。
- `netCents = 0`：不生成付款指令。

匹配算法：

1. 债务人按应付金额从大到小排序。
2. 债权人按应收金额从大到小排序。
3. 取当前最大债务人和最大债权人。
4. 生成金额为两者较小值的付款指令。
5. 扣减双方余额，余额为零的一方出队。
6. 重复直到所有余额结清。

一个债务人可以生成多条付款指令，一个债权人也可以收到多条付款指令。

### 5.3 保存结算批次

一个结算批次需要原子完成：

1. 读取全部未结算账目及其付款和分摊快照。
2. 生成 `SettlementLine` 和 `SettlementTransfer`。
3. 保存结算报告。
4. 将本次纳入的账目标记为 `SETTLED`。
5. 写入审计日志。
6. 提交事务。

结算阶段的唯一输入是账本 ID 和幂等键；不接收成员选择或分摊策略。

## 6. 多账目示例

第一天 `E1`：

```text
A 支付 20.00 元
分摊成员：A、B、C
分摊方式：平均
SplitShare：A 6.67、B 6.67、C 6.66
```

第二天 `E2`：

```text
B 支付 15.00 元
分摊成员：A、B
分摊方式：平均
SplitShare：A 7.50、B 7.50
```

按成员汇总：

```text
A = 20.00 - 6.67 - 7.50 = +5.83
B = 15.00 - 6.67 - 7.50 = +0.83
C = 0.00  - 6.66       = -6.66
```

所有金额都是整数分，合计为零。结算结果为：

```text
C -> A 5.83
C -> B 0.83
```

如果平均分摊余数分给其他成员，具体分摊金额会变化，但每条账目的分摊合计、成员净额合计和付款指令合计都必须保持精确为零。

## 7. 单人和多付款人

### 7.1 一名成员承担全部

A、B 实际付款 13 元和 7 元，但只选择 C 作为分摊成员：

```text
A 分摊 0
B 分摊 0
C 分摊 20.00
```

净额：

```text
A = +13.00
B = +7.00
C = -20.00
```

付款指令：

```text
C -> A 13.00
C -> B 7.00
```

### 7.2 多付款人

实际付款允许多条记录：

```text
A 付款 13.00
B 付款 7.00
```

付款合计必须等于 20.00。实际付款人和分摊成员可以是不同集合。

## 8. 稳定成员、成员有效期与重新加入

- 同一个用户在同一账本只有一个稳定 `LedgerMembership`，作为所有账目、分摊、结算和公平状态的成员身份。
- 加入、退出和重新加入使用多条 `MembershipPeriod` 记录；重新加入只新增有效期和新角色，不新建成员身份。
- 结算按稳定 `membershipId` 读取历史分摊和付款记录。
- 已提交账目不会因为成员退出、被移除或失联而重新分摊。
- 重新加入不会把旧账目重新挂接到新的有效期，也不会重算旧分摊；旧账目的归属仍由已冻结的 `SplitShare` 决定。
- B 已选入原分摊方案但后来离开时，B 仍作为同一稳定成员的历史债务人存在。
- B 的付款指令默认保持 `OPEN`，A 的应收不会被自动核销。
- 如果 A、C 决定承担 B 的欠款，必须新增明确的代付或坏账调整，并记录审计日志。
- `RoundingAllocationState` 绑定稳定成员身份；重新加入不重置游标和累计舍入应得额，成员不在账本期间也不会新增权益。
- 如果历史成员快照缺失，结算必须中止，不能静默修改分摊。

这里所说的隔离不是抹除同一用户的旧历史，而是：重新加入只新增有效期，账目和分摊不会重新计算或重新挂接。旧债务仍属于同一个稳定成员身份，并在历史账目和结算报告中可见。

需求中“重新加入产生新的成员关系”在本设计中映射为“新增 `MembershipPeriod`”；稳定 `LedgerMembership` 不改变。这样可保留同一人的公平状态和游标，同时由逐账目 `SplitShare` 保证不会把旧账目自动加入任何新方案。

## 9. 付款状态

`SettlementTransfer` 默认状态为 `OPEN`，表示系统生成了一笔待外部处理的付款指令。

允许状态：

- `OPEN`：尚未处理或无法确认。
- `MARKED_PAID_EXTERNALLY`：成员或管理员手动标记线下已处理。
- `WRITTEN_OFF`：经授权进行坏账核销。

系统不接入支付渠道，不自动确认真实到账。付款状态变更必须记录操作者、时间和原因。

## 10. 数据库表

| 表                          | 关键字段                                                                                      | 说明                                       |
| --------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `ledger_membership`         | `id`、`ledger_id`、`user_id`、`status`                                                        | 稳定的账本成员身份                         |
| `membership_period`         | `id`、`membership_id`、`role`、`joined_at`、`left_at`、`status`                               | 加入、退出、重新加入的有效期和角色         |
| `expense_entry`             | `id`、`ledger_id`、`amount`、`status`                                                         | 账目总额和生命周期                         |
| `expense_payment`           | `id`、`entry_id`、`payer_membership_id`、`amount`                                             | 一名成员的一次实际付款                     |
| `expense_split_plan`        | `id`、`entry_id`、`strategy_type`、`participant_count`、`cursor_before`、`cursor_after`       | 单笔账目的冻结分摊方案                     |
| `split_share`               | `id`、`split_plan_id`、`membership_id`、`amount_cents`、`rounding_adjustment_cents`           | 每个成员的分摊整数分和余数分调整           |
| `rounding_allocation_state` | `ledger_id`、`membership_id`、`numerator`、`denominator`、`version`                           | 每个成员关系的累计舍入应得额，不是货币余额 |
| `settlement_report`         | `id`、`ledger_id`、`generated_at`、`status`                                                   | 一次结算批次                               |
| `settlement_line`           | `id`、`report_id`、`membership_id`、`net_amount_cents`                                        | 成员汇总净额                               |
| `settlement_transfer`       | `id`、`report_id`、`debtor_membership_id`、`creditor_membership_id`、`amount_cents`、`status` | 付款指令                                   |

关键唯一约束：

- `ledger_membership(ledger_id, user_id)` 唯一，同一用户在同一账本始终使用同一稳定成员 ID。
- 同一 `LedgerMembership` 最多只有一条 `MembershipPeriod.status = ACTIVE` 的有效期记录。
- `expense_split_plan.entry_id` 在首版中唯一。
- `rounding_allocation_state(ledger_id, membership_id)` 唯一，重新加入不能创建第二条公平状态。
- `split_share(split_plan_id, membership_id)` 唯一。
- `expense_payment(entry_id, payer_membership_id)` 可以按付款人聚合，或允许多次付款但必须汇总。
- `settlement_transfer` 的付款边金额必须为正整数分。

### 10.1 有理数公平状态如何存储

`RoundingAllocationState` 不保存除法结果，而保存两个任意精度整数：

```text
numerator   = 分子（有符号）
denominator = 分母（必须大于 0）
```

建议表结构：

```sql
rounding_allocation_state (
  ledger_id      UUID        NOT NULL,
  membership_id  UUID        NOT NULL,
  numerator      NUMERIC     NOT NULL,
  denominator    NUMERIC     NOT NULL CHECK (denominator > 0),
  version        BIGINT      NOT NULL,
  updated_at     TIMESTAMP   NOT NULL,
  PRIMARY KEY (ledger_id, membership_id)
)
```

在 PostgreSQL 中使用无固定精度 `NUMERIC`；C# 应用层使用 `System.Numerics.BigInteger` 执行加减、比较和约分。如果目标数据库的 `DECIMAL` 有位数上限，则使用 `TEXT`/`VARBINARY` 保存 BigInteger 的十进制或二进制编码，所有运算仍在应用层完成。

每次更新后必须约分：

```text
g = gcd(abs(numerator), denominator)
numerator = numerator / g
denominator = denominator / g
```

该字段只用于余数分公平轮转，不是货币余额。C# 中禁止使用 `float`/`double`，金额使用 `decimal`，公平分数使用 `BigInteger`；也不把 `1/3` 写成有限小数。

## 11. 与结算周期的关系

```text
账目提交阶段：选择分摊成员、选择策略、生成并冻结 SplitShare
结算阶段：读取所有 SplitShare 和 ExpensePayment，按成员汇总，匹配债务人与债权人
```

因此：

- 不同账目可以有不同的分摊成员。
- 不同账目可以有不同的分摊策略。
- 结算时不需要再次选择成员或策略。
- 结算只选择结算批次中包含哪些未结算账目；首版为全量结算。

## 12. 算法不变量与测试

每次账目提交和结算必须验证：

1. 分摊成员人数大于等于 1。
2. 所有付款和分摊成员是创建方案时的有效成员，角色高于只读访客。
3. 每条账目的付款金额合计等于账目金额。
4. 每条账目的分摊金额合计等于账目金额。
5. 平均分摊余数分已经分配给具体成员，不能存在无主尾差。
6. 手工分摊成员集合与金额映射集合完全一致。
7. 手工分摊每个金额大于 0，并精确到分。
8. 所有成员精确净额之和为零。
9. 每条付款指令金额大于零，付款双方不为自己。
10. 所有付款指令金额之和等于所有债务人应付总额。
11. 结算重复提交不产生重复付款指令。
12. 成员退出和重新加入只新增 `MembershipPeriod`，不改变稳定成员 ID、历史分摊、债务或 `RoundingAllocationState`。
13. 每次分配余数分后，所有 `RoundingAllocationState` 的分数应得额精确合计为零。
14. 任意成员的实际余数收益与理论应得额之差小于 1 分。
15. 重复模拟相同参与者时，额外 1 分获得频率收敛到 `remainder / n`。

## 14. UML 与数据库对应

- `ExpenseEntry` 与 `ExpenseSplitPlan` 是一对一。
- `ExpenseSplitPlan` 与 `SplitShare` 是一对多。
- `ExpensePayment` 记录实际付款，分摊成员和实际付款人可以不同。
- `SplitRequest` 携带参与者集合和手工金额映射。
- `SplitStrategy` 只计算整数分分摊结果，不查询成员角色。
- `RoundingAllocationState` 用精确分子/分母记录每个历史成员关系的累计舍入应得额，不属于货币余额。
- `SettlementMatcher` 只汇总整数分净额并生成付款边。
- `SettlementTransfer` 默认 `OPEN`，不自动确认到账。

## 15. C#/.NET 实现映射

算法本身保持语言中立，当前计划使用 C#/.NET 实现时可以映射为：

| 设计概念     | C#/.NET 实现                                       |
| ------------ | -------------------------------------------------- |
| 金额         | `decimal`；禁止 `float`/`double`                   |
| 整数分       | `long`；所有金额校验和结算内部统一为分             |
| 公平分数     | `System.Numerics.BigInteger` 分子和分母            |
| ID           | `Guid`                                             |
| 时间         | `DateTimeOffset`                                   |
| 手工金额映射 | `Dictionary<Guid, decimal>`                        |
| 分摊策略     | `ISplitStrategy.Split(SplitRequest request)`       |
| 后端         | ASP.NET Core Web API + Entity Framework Core       |
| 数据访问事务 | EF Core `DbContext.Database.BeginTransactionAsync` |
| 并发控制     | `rowversion` 或 `ConcurrencyToken`                 |

数据库金额字段建议使用 `decimal(20,2)`，与 C# `decimal` 对应；公平状态分子/分母使用数据库 `NUMERIC` 保存任意精度整数。若数据库不支持任意精度 `NUMERIC`，则把 BigInteger 序列化为十进制文本，并在 C# 服务层完成运算。

本算法取代此前的 AA 专用算法和公共尾差池方案。每笔账目在冻结分摊方案时已经精确到分，结算阶段不存在循环小数或无主尾差。
