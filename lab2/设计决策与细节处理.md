## 1. 决策原则

未确认细节按以下顺序取舍：

1. 数据安全优先于操作便利，所有关键变更必须可审计。
2. 金额、权限和结算状态以数据库事务保证一致性。
3. 默认采用结构简单、后续易扩展的实现，不引入超出课程原型需要的复杂能力。
4. 对无法满足的规则返回明确错误，不静默修改用户数据。
5. 未明确开放的能力默认不开放，待后续需求确认后再扩展。

## 6. 审批、修改与状态流转

相关需求：`REQ-003`、`REQ-004`、`REQ-014`、`REQ-015`、`REQ-025`、`REQ-030`

采用的完整状态规则：

- 普通成员提交新增或修改后进入 `PENDING`。
- 命中免审规则时直接进入 `ACTIVE`。
- 管理员直接新增时直接进入 `ACTIVE`。
- 申请人撤回待审核申请后回到 `DRAFT`，可修改后重新提交。
- 管理员批准后进入 `ACTIVE`；驳回后进入 `REJECTED`。
- `REJECTED` 记录保持只读，用户可复制其内容生成新的草稿，不原地覆盖旧记录。
- `ACTIVE` 可以修改，修改时新增 `ChangeRecord`，不覆盖历史修改记录。
- `ACTIVE` 纳入结算后进入 `SETTLED`，禁止继续修改、删除或撤销。
- `ACTIVE` 被撤销后进入 `REVOKED`。
- `DRAFT` 删除、`ACTIVE` 删除/作废/撤销统一使用撤销语义；`REVOKED` 首版不可恢复。
- `SETTLED` 或 `REVOKED` 的订正通过新账目完成，原记录永久保留。

并发与审批规则：

| 项目 | 采用的默认方案 |
| --- | --- |
| 待审修改数量 | 同一账目最多存在一条 `PENDING` 修改申请 |
| 同一申请人重复提交 | 新提交覆盖其本人尚未处理的修改申请，并保留操作日志 |
| 不同申请人冲突 | 已有其他人待审修改时拒绝新申请，提示先撤回或等待处理 |
| 并发审批 | `ApprovalRequest` 和 `ExpenseEntry` 使用版本号乐观锁；第一个提交成功，其余返回冲突 |
| 自我审批 | 禁止审批自己提交的申请 |
| 撤回权限 | 只有原申请人可以撤回待审核申请 |
| 撤销理由 | 管理员或所有者撤销生效账目时必须填写理由 |
| 修改记录可见性 | 当前有效账本成员可查看完整修改时间、操作者和前后值；退出成员不可访问 |

## 7. 通用结账
相关需求：`REQ-008`、`REQ-009`、`REQ-018`、`REQ-021`、`REQ-024`

| 项目 | 采用的默认方案 |
| --- | --- |
| 空账本 | 没有未结算账目时禁用结算按钮，不生成空报告 |
| 结算范围 | 首版对账本内全部未结算账目进行全量结算，不支持部分勾选 |
| 重复结算 | 同一请求使用 `Idempotency-Key`，重复提交返回原报告 |
| 并发修改 | 结算事务锁定账本和待结算账目；版本冲突时整笔回滚并提示重试 |
| 金额结构 | 数据库使用 `DECIMAL(20,2)` 元，计算统一转换为整数分；禁止浮点数 |
| 逐账目分摊 | 每个账目独立保存 `ExpenseSplitPlan` 和 `SplitShare`，不同账目可使用不同成员和策略 |
| 平均分摊 | 整数分除法，基础份额加余数分；余数分优先给累计舍入应得额最大的成员 |
| 手工分摊 | 已选成员金额均大于 0，集合完全匹配，合计必须等于账目金额 |
| 结算输入 | 只读取已冻结的付款和分摊快照，不再选择成员或执行分摊策略 |
| 净额口径 | `netCents = sum(付款分) - sum(分摊分)`，所有成员净额之和必须为零 |
| 公平轮转 | `RoundingAllocationState` 按账本和成员关系保存精确分数应得额；累计应得额相同时才使用账本游标和成员 ID 决胜 |
| 付款匹配 | 正净额为债权、负净额为债务；按金额和成员关系 ID 排序后用双指针生成付款边 |
| 报告快照 | `SettlementLine` 保存成员分摊合计和最终净额，`SettlementTransfer` 保存付款指令 |
| 转账 | 系统只生成付款指令并标记 `OPEN`，不发起、接收或确认真实转账 |

### 7.1 通用结账算法

完整算法见 `通用结账算法.md`，执行顺序为：

1. 每笔账目在提交时独立选择分摊成员和策略，生成整数分 `SplitShare` 并冻结。
2. 结算读取所有未结算账目的付款和分摊快照。
3. 按成员关系汇总净额，所有净额均为整数分且合计为零。
4. 将正净额作为债权、负净额作为债务，执行双指针匹配。
5. 保存付款指令、结算报告、账目结清状态和审计日志。

平均分摊的余数在账目分摊阶段已经分配，因此结算阶段没有公共尾差池，也不存在循环小数。每次平均分摊先给已选成员增加理论余数应得额 `remainder / participantCount`，再优先把 1 分分配给累计应得额最大的成员，并从其应得额中扣除 1 分；所有成员应得额精确合计为零。

### 7.2 垫付人在结算前被移除

- 移除成员只终止其当前权限，不删除旧账目和旧分摊快照。
- 结算按历史 `membershipId` 计算，不要求该成员当前仍为 `ACTIVE`。
- 债务人仍向历史垫付人的成员关系付款，系统不重新分摊原账目。
- 结算页不重新显示成员选择器；即使 B 已从当前成员列表消失，也必须从冻结的分摊明细中找到 B 的历史成员关系。
- B 失联或拒付时付款指令保持 `OPEN`，A 的应收不能自动核销；代付或坏账处理必须创建显式调整并审计。
- 若 A 是所有者，必须先转移所有权；首版没有转移能力时拒绝移除。

### 7.3 移除后重新加入

- 同一个用户在同一账本始终只有一个稳定的 `LedgerMembership`，不因重新加入创建新成员。
- 加入、退出和重新加入分别由 `MembershipPeriod` 记录；重新加入只新增有效期和新角色，不改变稳定成员 ID。
- 每笔账目的 `ExpenseSplitPlan` 和 `SplitShare` 已经固定，重新加入不会自动把这些账目重新挂到新有效期，也不会重算分摊。
- 历史分摊、付款和付款指令继续按同一个稳定成员 ID 归属；新账目只有被明确选中时才加入新的分摊方案。
- `RoundingAllocationState` 按稳定成员 ID 保存，重新加入不重置游标和累计舍入应得额；成员不在账本期间不会产生新的余数权益。
- 旧角色和旧待审申请不因重新加入而恢复；当前权限由最新有效 `MembershipPeriod` 决定。

## 9. 通知与审计

相关需求：`REQ-007`、`REQ-020`、`REQ-029`

通知规则：

- 管理员或所有者处理他人创建的账目时，系统生成应用内通知。
- 操作者处理自己创建的账目时不通知自己。
- 通知保存于共享数据库，手机应用和微信小程序读取同一份未读状态。
- 用户离线时通知保留，下一次登录后展示。
- 通知保留 90 天；用户可标记已读或全部已读。
- 首版不接入短信、邮件或微信模板消息。

审计规则：

- 日志记录操作者、账本、操作类型、目标对象、处理结果、请求 ID 和时间。
- 申请、审批、免审写入、修改、撤销、结算、角色变更和成员移除均留痕。
- 被拒绝的越权操作和校验失败的关键操作记录失败日志。
- 日志只允许追加，不提供应用内删除入口。
- 操作日志仅管理员和所有者可查看；普通成员可查看账目内部的修改记录。
- 业务变更和审计日志在同一数据库事务内提交。
- 日志至少保留 2 年；生产环境建议每日备份并保留 30 天。

## 11. 性能验收口径

相关需求：`REQ-028`

- 数据规模按 10,000 名用户设计。
- 查询场景支持 100 个并发请求。
- 查询接口目标：P95 响应时间不超过 500 ms，P99 不超过 1 s。
- 请求成功率达到 99% 以上，接口超时时间设为 5 s。
- 索引至少覆盖账本 ID、成员 ID、账目发生时间、账目状态和垫付者。
- 验收时应记录并发请求数、成功数、失败数、P95/P99 和资源使用情况。

## 12. 首版明确不做

以下能力不属于首版范围，避免实现阶段继续扩张：

- 自助密码找回和第三方登录。
- 账本自定义分类。
- 部分账目结算。
- 已结清或已撤销账目的原地恢复。
- 真实支付、自动转账和到账确认。
- 汇款凭证上传。
- 普通成员查看全账本操作日志。
- 短信、邮件和微信模板消息推送。

## 14. 账目修改记录查询

`ChangeRecord` 采用追加写入，不允许覆盖旧记录。每条记录必须包含：

- `EntryId`：关联账目。
- `ChangeNo`：该账目内单调递增的修改序号。
- `ChangedAt`、`OperatorUserId`、`BeforeSnapshot`、`AfterSnapshot`。

数据库建立唯一复合索引：

```sql
UNIQUE INDEX IX_change_record_entry_change_no
ON change_record (entry_id, change_no);
```

C# 实体查询使用 EF Core：

```csharp
var records = await db.ChangeRecords
    .AsNoTracking()
    .Where(x => x.EntryId == entryId)
    .OrderBy(x => x.ChangeNo)
    .Select(x => new ChangeRecordDto(
        x.ChangeNo,
        x.ChangedAt,
        x.OperatorUserId,
        x.BeforeSnapshot,
        x.AfterSnapshot))
    .ToListAsync(cancellationToken);
```

如果记录很多，接口使用游标分页，而不是一次性加载全部 JSON：

```text
GET /api/expenses/{entryId}/changes?afterChangeNo=120&pageSize=50
```

查询条件始终增加 `EntryId`，不要按 `ChangedAt` 做全表范围扫描。`BeforeSnapshot`、`AfterSnapshot` 只作为返回数据，不参与索引。

`ChangeNo` 在账目修改事务内分配并随账目版本号一起更新。若两个并发修改同时发生，行锁或乐观并发控制保证同一账目不会得到重复序号。

查看修改记录前仍需校验当前用户属于目标账本且有查看权限。若需要把申请、审批和修改显示为统一时间线，可以额外按 `AuditLog(ledger_id, target_type, target_id, created_at)` 建立索引，但账目自身的修改详情仍以 `ChangeRecord` 为准。
