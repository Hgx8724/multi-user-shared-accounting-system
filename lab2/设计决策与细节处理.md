## 1. 决策原则

未确认细节按以下顺序取舍：

1. 数据安全优先于操作便利，所有关键变更必须可审计。
2. 金额、权限和结算状态以数据库事务保证一致性。
3. 默认采用结构简单、后续易扩展的实现，不引入超出课程原型需要的复杂能力。
4. 对无法满足的规则返回明确错误，不静默修改用户数据。
5. 未明确开放的能力默认不开放，待后续需求确认后再扩展。

## 2. 身份认证与账号

相关需求：`REQ-027`

| 项目 | 采用的默认方案 |
| --- | --- |
| 注册 | 开放用户名注册；注册入口在服务端统一校验 |
| 用户名 | 全系统唯一，忽略大小写；长度 3 至 32 位；仅允许字母、数字和下划线 |
| 密码 | 至少 8 位；使用带随机盐的 BCrypt 保存，禁止保存明文或可逆密文 |
| 会话 | 登录成功签发短期 Access Token（30 分钟）和可撤销 Refresh Token（30 天）；允许同一账号多设备登录 |
| 注销 | 注销当前会话时撤销当前 Refresh Token；修改密码后撤销该账号全部旧会话 |
| 登录失败 | 同一用户名连续失败 5 次后临时锁定 15 分钟；成功认证后清零失败计数 |
| 密码找回 | 首版不提供自助找回；预留邮件或短信验证码接口，不在首版伪造未确认的身份验证渠道 |
| 多认证绑定 | 每种认证方式通过 `AuthBinding` 关联同一个 `UserAccount`，认证方式不同但内部用户 ID 相同 |

## 6. 审批、修改与状态流转

相关需求：`REQ-003`、`REQ-004`、`REQ-014`、`REQ-015`、`REQ-025`、`REQ-030`

采用的完整状态规则：

- 普通成员提交新增或修改后进入 `PENDING`。
- 命中免审规则时直接进入 `ACTIVE`。
- 管理员直接新增时直接进入 `ACTIVE`。
- 申请人撤回待审核申请后回到 `DRAFT`，可修改后重新提交。
- 管理员批准后进入 `ACTIVE`；驳回后进入 `REJECTED`。
- `REJECTED` 记录保持只读，用户可复制其内容生成新的草稿，不原地覆盖旧记录。
- `ACTIVE` 可以修改，修改时新增 `ChangeRecord`，不覆盖历史修改记录。
- `ACTIVE` 纳入结算后进入 `SETTLED`，禁止继续修改、删除或撤销。
- `ACTIVE` 被撤销后进入 `REVOKED`。
- `DRAFT` 删除、`ACTIVE` 删除/作废/撤销统一使用撤销语义；`REVOKED` 首版不可恢复。
- `SETTLED` 或 `REVOKED` 的订正通过新账目完成，原记录永久保留。

并发与审批规则：

| 项目 | 采用的默认方案 |
| --- | --- |
| 待审修改数量 | 同一账目最多存在一条 `PENDING` 修改申请 |
| 同一申请人重复提交 | 新提交覆盖其本人尚未处理的修改申请，并保留操作日志 |
| 不同申请人冲突 | 已有其他人待审修改时拒绝新申请，提示先撤回或等待处理 |
| 并发审批 | `ApprovalRequest` 和 `ExpenseEntry` 使用版本号乐观锁；第一个提交成功，其余返回冲突 |
| 自我审批 | 禁止审批自己提交的申请 |
| 撤回权限 | 只有原申请人可以撤回待审核申请 |
| 撤销理由 | 管理员或所有者撤销生效账目时必须填写理由 |
| 修改记录可见性 | 当前有效账本成员可查看完整修改时间、操作者和前后值；退出成员不可访问 |

## 7. 结算与尾差

相关需求：`REQ-008`、`REQ-009`、`REQ-018`、`REQ-021`、`REQ-024`

| 项目 | 采用的默认方案 |
| --- | --- |
| 空账本 | 没有未结算账目时禁用结算按钮，不生成空报告 |
| 结算范围 | 首版对账本内全部未结算账目进行全量结算，不支持部分勾选 |
| 重复结算 | 已结清账目不会再次进入下一期；同一请求使用 `Idempotency-Key`，重复提交返回同一报告 |
| 并发修改 | 结算事务锁定账本和待结算账目；版本冲突时整笔回滚并提示重试 |
| 金额结构 | 数据库统一使用 `DECIMAL(20,6)` 元，代码使用 `BigDecimal`；用户输入仍限制为精确到 0.01 元 |
| 分摊计算 | 平均分摊先按 6 位小数计算精确值；精确分摊只用于余额计算，不直接把每个人的净额截断成不等长账本 |
| 手工分摊 | 手工分摊金额合计必须与账目金额精确到分相等，否则拒绝提交 |
| 净额口径 | 先计算每个成员关系的精确净额 `已支付 - 应分摊 + 期初尾差`；所有成员精确净额之和必须为零 |
| 付款匹配 | 先完成零和量化；再将负净额作为付款人、正净额作为收款人，按金额从大到小、再按成员关系 ID 排序，逐笔生成债务人到债权人的付款边 |
| 取整规则 | 使用最大余数法和账本轮转游标把精确净额量化到整数分，确保所有量化净额之和为零；小数部分相同的成员按轮转顺序分配额外 1 分 |
| 尾差记录 | `RoundingBalance` 按“账本 + 成员关系”保存，只保留非零行；正数表示待收，负数表示待付，所有成员尾差之和为零 |
| 平衡记录 | 结算报告保存精确净额、本期付款边和期末尾差，便于复核；不使用来历不明的单一“尾差账户”冲账 |
| 下一周期 | 下一期先把每个成员关系的期末尾差加入其期初精确净额，再重新匹配付款边 |
| 尾差权限 | 用户不能直接编辑尾差，只能由结算服务自动更新 |
| 报告快照 | `SettlementLine` 保存精确分摊、精确净额、本期实结、结转金额及付款边；成员退出后报告仍可追溯 |
| 并发安全 | 更新尾差时锁定账本余额行，使用版本号和幂等键；报告、结清、尾差和审计日志同一事务提交 |
| 转账 | 系统只生成报告和标记结清，不发起、接收或确认真实转账 |

### 7.1 AA 结算算法

完整算法见 `AA制结算算法.md`，执行顺序为：

1. 按成员关系计算精确净额，所有精确净额之和为零。
2. 使用最大余数法和账本轮转游标，将精确净额零和量化到整数分。
3. 将量化后的正净额视为债权、负净额视为债务，执行债务人到债权人的双指针匹配。
4. 将精确净额与量化净额之间的差异保存为具体成员关系的 `RoundingBalance`。
5. 保存付款指令、结算报告、尾差、账目结清状态和审计日志。

不允许出现无主尾差池。例如 `A +13.34、B -6.66、C -6.66` 合计为 `+0.02`，不能作为最终结算结果；必须先完成零和量化。

### 7.2 垫付人在结算前被移除

- 移除成员只终止其当前权限，不删除旧账目、旧分摊和旧尾差。
- 结算按历史 `membershipId` 计算，不要求该成员当前仍为 `ACTIVE`。
- 债务人仍向历史垫付人的成员关系付款，系统不重新分摊原账目。
- 报告显示“A（已退出）”及成员关系快照；实际转账仍由成员线下完成。
- 若 A 是所有者，必须先转移所有权；首版没有转移能力时拒绝移除。

### 7.3 移除后重新加入再结算

- 旧成员关系 `M1` 和新成员关系 `M2` 分别计算，不按用户 ID 合并。
- 旧账目的分摊和尾差仍归 `M1`，新账目才归 `M2`。
- 报告中可出现“A（历史成员 M1）”和“A（当前成员 M2）”两行。
- 同一用户作为收款人时，界面可以合并展示总收款额，但底层付款指令必须保留两条成员关系归属。
- 重新加入不会恢复旧角色、旧待审申请或旧尾差。

## 9. 通知与审计

相关需求：`REQ-007`、`REQ-020`、`REQ-029`

通知规则：

- 管理员或所有者处理他人创建的账目时，系统生成应用内通知。
- 操作者处理自己创建的账目时不通知自己。
- 通知保存于共享数据库，手机应用和微信小程序读取同一份未读状态。
- 用户离线时通知保留，下一次登录后展示。
- 通知保留 90 天；用户可标记已读或全部已读。
- 首版不接入短信、邮件或微信模板消息。

审计规则：

- 日志记录操作者、账本、操作类型、目标对象、处理结果、请求 ID 和时间。
- 申请、审批、免审写入、修改、撤销、结算、角色变更和成员移除均留痕。
- 被拒绝的越权操作和校验失败的关键操作记录失败日志。
- 日志只允许追加，不提供应用内删除入口。
- 操作日志仅管理员和所有者可查看；普通成员可查看账目内部的修改记录。
- 业务变更和审计日志在同一数据库事务内提交。
- 日志至少保留 2 年；生产环境建议每日备份并保留 30 天。

## 11. 性能验收口径

相关需求：`REQ-028`

- 数据规模按 10,000 名用户设计。
- 查询场景支持 100 个并发请求。
- 查询接口目标：P95 响应时间不超过 500 ms，P99 不超过 1 s。
- 请求成功率达到 99% 以上，接口超时时间设为 5 s。
- 索引至少覆盖账本 ID、成员 ID、账目发生时间、账目状态和垫付者。
- 验收时应记录并发请求数、成功数、失败数、P95/P99 和资源使用情况。

## 12. 首版明确不做

以下能力不属于首版范围，避免实现阶段继续扩张：

- 自助密码找回和第三方登录。
- 账本自定义分类。
- 部分账目结算。
- 已结清或已撤销账目的原地恢复。
- 真实支付、自动转账和到账确认。
- 汇款凭证上传。
- 普通成员查看全账本操作日志。
- 短信、邮件和微信模板消息推送。

## 13. 对 UML 的同步结果

- 类图增加账目发生时间 `occurredAt` 和订正来源 `correctionOfEntryId`；金额由整数分改为 `BigDecimal` / `DECIMAL(20,6)`。
- `RoundingBalance` 改为按账本和历史成员关系保存零和尾差，并新增 `SettlementTransfer` 表示债务人到债权人的付款指令。
- 用例图明确只读访客不可导出，普通成员及以上角色可导出。
- 状态图增加“待审核撤回至草稿”，并明确驳回、结清和撤销后的处理方式。
- 时序图加入 `SettlementMatcher`，明确精确净额、零和量化、债务匹配、付款指令、期初/期末尾差和事务提交。
- 组件图继续采用手机应用与微信小程序共享后端的设计。

上述方案作为实验二的设计基线；若后续甲方确认不同规则，应优先更新本文和对应 PlantUML 源文件，再重新生成 PNG。
